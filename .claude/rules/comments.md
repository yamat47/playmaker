# コメント規約

コメントの基準は `writing-conventions` skill（`references/code-comments.md` と `references/what-goes-where.md`）である。
コメントには、なぜ素直な書き方を選ばなかったか（Why not）と、型で表せない制約だけを書く。
この文書には、skill に書かれていないこのリポジトリ固有の決まりと、skill と扱いを変える点だけを置く。

## 書くもの

- 公開 API（`src/playmaker.ts` から export するもの）の JSDoc には、型で表せない契約、失敗したときの挙動、既定値を書く。
  名前や型をそのまま文章にした説明は書かない。
- `biome-ignore` と `v8 ignore` には、抑制が必要な理由を必ず添える。
  `v8 ignore` の理由は「その分岐に到達できない理由」であり、カバレッジの数字ではない。

## 書かないもの

- PRD の章番号や節名を参照しない。制約の理由は、その場で文章として書く。
  PRD が変わると参照だけが残って嘘になるため。
- ファイル冒頭に、役割や層を説明する定型ブロックを置かない。
  役割はファイル名とエクスポートで表す。
- 呼び出し元を名指ししない（「Toolbar が読む」「playmaker.ts から呼ばれる」など）。
  呼ばれる側が使われ方を知ることになり、呼び出し元が変わると古くなる。
- `// --- 内部 ---` や `// 状態の読み取り` のような区切り見出しを置かない。構造はファイル分割と関数で表す。
- カバレッジの数字（「100% を保つため」など）を Why にしない。
- M0 から M9 やテーマ番号など、進め方の痕跡を残さない。経緯は git 履歴と `docs/plans/` に置く。

## 書き方

- 文は「。」で終える。1 行のコメントも同じ。
- 矢印（→）や「＝」で語をつなぐ略記を書かない。文として書く。
  ただし数式と、座標変換の向きを示す短い注記（`px→yard` 程度）はよい。
- em dash を使わない。文を切るか、括弧を使う。

## TODO

コードに TODO を残さない。やり残しは `docs/plans/` の計画に書く。
skill にある「予定している機能が挙動を変える場所に TODO を残す」という Preference は、このリポジトリでは使わない。
計画のほうが先に更新され、コード側の TODO だけが古くなるため。
